A capability-based specification for a generic product, expanded from the supplied requirement sample and informed by official reference documentation.
Every numbered entry contains a proposed system requirement and a verification checkpoint. Interface placement, vendor-specific engines, and application branding are not implementation requirements.
Reference applications: Microsoft Word, Excel, PowerPoint, and OneNote.
Reference scope: principally Microsoft 365 desktop on Windows; exceptions are identified.
Prepared: 19 September 2026  |  Specification version: 1.0
How to use this specification
Purpose and evidence
This is an original requirements catalogue for a new generic productivity product. The supplied sample establishes the requested “The system shall …” format and initial capability areas [U1]. Official documentation provides reference behavior and version context [M01–M28]. The acceptance checks, safety rules, and architectural boundaries are proposed design decisions; they are not claims about how the reference applications are internally implemented.
Coverage boundary
The catalogue inventories named actions and command families across normal editing, contextual object editing, file management, review, developer workflows, and selected optional extensions. Related choices appear in each requirement title; each named choice is part of the requirement’s verification scope. Shared capabilities are specified once and inherited only where applicable.
This is not a certified, build-exact inventory of every control in every edition. No installed application build was mechanically enumerated. Names and availability can vary with platform, update channel, subscription, organization policy, selected content, and installed extensions. Arbitrary third-party commands and every item in open-ended galleries are outside the fixed inventory. Release-specific catalogues are governed by REQ-ENG-TEST-03. [M01–M04; M10; M18–M20]

A profile marker is not a delivery-priority estimate. “Supported” or “declared” refers to an explicit, versioned capability manifest—not an unspecified loophole. The product team must record supported variants and exclusions before implementation and acceptance.

Dependency rules
Workspace-specific requirements add to COM-* and the eligible OBJ-* services; they do not replace them. A document table, a grid table, and a note table remain different object types. Protection rules apply to every export, search, preview, and automation path, not just ordinary editing. Optional connected features must leave core content accessible when the service is unavailable.
Reference-version cautions
Presentation comparison and merge are retained here only as a legacy option: Microsoft documents their removal from Windows subscription builds starting with version 2502. The slide-reuse reference describes local-file import and notes that cloud reuse is deprecated. [M18; M19]
Notebook requirements use the Windows desktop notebook application as the main reference, not a blended feature list from all notebook editions. Python-compatible computation, script services, mathematical assistance, and AI features are optional. External scheduling is modeled as a provider integration rather than an assumed editor-native command. [M10; M11; M20; M23; M24]

COM-LIFE  |  Content lifecycle and persistence
Applicability: All workspaces; explicit file saving and continuously saved notebooks use distinct state models.
Reference basis: [U1]  [M01]  [M02]  [M03]  [M04]. Requirement wording and acceptance checks are proposed product design.
REQ-COM-LIFE-01  |  New; blank content; template creation  [B]
The system shall create a new document, workbook, presentation, or notebook from a blank definition or a selected template without modifying the template.
Acceptance: New content receives an independent identity and editable state.
REQ-COM-LIFE-02  |  Open; browse; recent items  [B]
The system shall open supported content from local storage and authorized repositories, retaining a recent-item history that users can clear.
Acceptance: Inaccessible, missing, and unsupported items produce distinct recoverable errors.
REQ-COM-LIFE-03  |  Pin; unpin; favorite  [B]
The system shall let users pin and unpin frequently used items and locations independently of recent-access ordering.
Acceptance: Pinned items survive application restart and remain permission-checked.
REQ-COM-LIFE-04  |  Save; save all  [B]
The system shall persist changes to writable content and expose saved, saving, unsaved, failed, and read-only states.
Acceptance: A failed write does not replace the last valid saved version.
REQ-COM-LIFE-05  |  Save as; save a copy; rename  [B]
The system shall create a separately named copy or rename the current item, clearly distinguishing those operations and their link consequences.
Acceptance: Saving a copy leaves the original content and identity unchanged.
REQ-COM-LIFE-06  |  Automatic saving  [B]
The system shall support continuous saving for eligible storage providers and display whether automatic saving is active or unavailable.
Acceptance: Users can distinguish locally saved changes from remotely synchronized changes.
REQ-COM-LIFE-07  |  Recovery; restore unsaved content  [B]
The system shall retain recoverable checkpoints according to configured policy and offer recovery after abnormal termination.
Acceptance: Recovery identifies checkpoint time and does not silently overwrite newer content.
REQ-COM-LIFE-08  |  Close; exit  [B]
The system shall close content or the application after handling unsaved changes and incomplete operations through explicit choices.
Acceptance: Canceling a close preserves the active editing session.
REQ-COM-LIFE-09  |  Read-only; edit a copy  [B]
The system shall allow viewing of nonwritable content and offer an editable copy when permissions and policy allow.
Acceptance: Read-only mode cannot change the protected source.
REQ-COM-LIFE-10  |  Properties; author; title; subject; keywords  [B]
The system shall view and edit supported content metadata with appropriate field validation and permission checks.
Acceptance: Modified metadata persists through a save and reopen cycle.
REQ-COM-LIFE-11  |  Location; move; copy path  [B]
The system shall display the storage location and support authorized moves and copying of resolvable item references.
Acceptance: A failed move leaves a recoverable source and reports its outcome.
REQ-COM-LIFE-12  |  Version history; restore version  [B]
The system shall list available saved versions with timestamps and authors and restore a selected version without concealing subsequent history.
Acceptance: Restoring creates a traceable current version rather than erasing audit history.
REQ-COM-LIFE-13  |  Delete; recover deleted item  [B]
The system shall provide deletion and recovery where supported by the storage provider, disclosing retention and permanent-deletion consequences.
Acceptance: Restorable and permanently removed items are clearly distinguished.
REQ-COM-LIFE-14  |  Manage links; missing dependencies  [B]
The system shall identify external content dependencies and let users update, relocate, break, or preserve supported links.
Acceptance: Broken links show their target and do not silently resolve to unrelated content.
REQ-COM-LIFE-15  |  Package validation; repair  [B]
The system shall detect corrupt or incomplete packages and offer repair or read-only recovery with a loss report.
Acceptance: Repaired content is saved separately unless replacement is explicitly approved.

Appendix B  |  Normalization and implementation boundaries
The following are deliberate transformations of the sample, not silent claims that its implementation details were verified. They separate required outcomes from technology choices and add testable boundaries. [U1]
SAMPLE ASSUMPTIONREQUIREMENT TREATMENTNamed package formats and operating-system object technologiesKeep explicit interoperability targets where useful. Treat native content storage, cross-process activation, and object adapters as architecture decisions rather than universal dependencies.Fixed encryption algorithm, key derivation, or rights-management providerRequire approved encryption and authorization behavior. Select algorithms, key handling, policy providers, and compatibility rules in the security design; the sample alone does not establish reference-product internals.A strictly acyclic formula graph plus circular calculationsRequire dependency tracking, explicit cycle detection, and separately enabled iterative calculation. Do not assume an acyclic graph in every valid workbook state.An unspecified library of thousands of functionsRequire a versioned function manifest with names, signatures, tested semantics, and limitations. A function count is not a substitute for compatibility evidence. [M09]Specific query and analytical-model enginesSpecify extraction, transformation, relationships, measures, refresh, and model behavior. Compatibility with a named language can be an optional adapter requirement rather than a mandated internal engine.A zero-latency live drawing layerRequire published latency budgets and measured results on reference hardware. No implementation is assumed to have literally zero latency.A fixed retention duration for deleted notesMake retention a declared storage or organizational policy and disclose restore eligibility. Do not hard-code a sample duration as a cross-provider requirement.A simple arithmetic result treated like a dynamic formula cellSpecify explicit note-expression evaluation separately from live spreadsheet recalculation and optional symbolic assistance. [M23]Universal grammar, recognition, or mathematical assistanceScope proofing, handwriting recognition, speech services, and advanced solving to declared language, platform, device, and provider profiles.One universal notebook hierarchy or synchronization mechanismRequire valid notebook, section-group, section, and page relationships without mandating a fixed internal layer count, binary-delta format, or conflict algorithm.Vendor branding used as an architectural dependencyUse generic services such as query transformation, analytical models, structured diagrams, camera objects, and assisted authoring. Source names remain only in provenance and compatibility notes.Every variant in every gallery treated as a separate fixed requirementEnumerate command families here and require versioned gallery manifests. Each shipped chart, effect, style, connector, template, or function variant needs its own conformance fixture.
Appendix C  |  Adoption and acceptance contract
The catalogue is ready to become a product backlog, but choosing a generic product scope is distinct from claiming feature-for-feature compatibility with a particular desktop build. Before delivery, record the following decisions against the relevant requirements.
DECISIONREQUIRED RECORDWorkspace scopeWhich of document, grid, presentation, and notebook workspaces are included; the shared services inherited by each.Optional and legacy profilesThe selected O and L requirements, their providers, supported platforms, license dependencies, and disabled-state behavior.Formats and compatibilityImport, editable-save, export, print, and legacy formats; exact preservation guarantees and known exceptions.Capability cataloguesImplemented function signatures, chart variants, transitions, animations, templates, recognition languages, and external connectors.Security and privacyIdentity boundaries, cryptographic profiles, key management, trust policies, retention, external transmission, and audit scope.Performance and numerical budgetsReference hardware and workloads; maximum supported content sizes; latency targets and analytical tolerances.Verification evidenceRequirement identifier, named variant, test case, fixture, result, defect reference, and release status for each adopted behavior.
Minimum verification pattern
For each adopted requirement, verify the normal case, invalid input, cancellation or failure, save-and-reopen behavior, permission denial, and undo or recovery where relevant. Add locale, accessibility, concurrent-edit, and import/export fixtures when the behavior depends on them. Each listed command variant requires coverage; one successful variant does not satisfy a whole grouped requirement.
Acceptance-check example
REQ-GRID-EDIT-16 — In-cell checkboxes. Begin with an unchecked Boolean cell. Toggle it using a pointer and then the keyboard. Verify the resulting Boolean value in a dependent formula, save and reopen, remove the checkbox formatting while retaining the value, and confirm that a protected cell cannot be changed through either input method. The catalogue’s short acceptance line is the checkpoint; this expanded scenario illustrates the expected test depth.
Delivery-status convention
Track selected requirements as planned, implemented, verified, partial, deferred, or excluded. A partial item must list unsupported named variants. A requirement is verified only when its acceptance evidence matches the published platform and capability profile. Do not substitute a rendered preview for editable format support or a connected service for an undisclosed offline guarantee.
